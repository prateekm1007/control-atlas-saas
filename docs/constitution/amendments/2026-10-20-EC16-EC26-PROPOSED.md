## EC-16 — Remote-verifiable claims

**Failure pattern (verbatim).** Reported commit SHAs that aren't on GitHub. Round-13 reported seven, none on the remote.

**Rule (verbatim).** **EC-16 Remote-verifiable claims.** A result counts only if its commit is on a remote, and its SHA is in the report.

**Enforcement (verbatim).** CI reads the PR description and checks each listed SHA with `git ls-remote`.

**Implementation mapping.** Enforcement point: `proposals/ci/verify-claimed-shas.yml` → `scripts/ci/verify_claimed_shas.py`. PR body carries a machine-readable field `Claimed-SHAs:` (one full 40-hex SHA per line). CI fails on any listed SHA absent from the remote, and on an empty/missing field when the PR claims results.

**Corrections (recorded, not silently applied).**
1. `git ls-remote` resolves only ref tips. A SHA that exists on the remote but is not a ref tip — e.g. the base of a pushed branch, any mid-branch commit, or a commit on a since-deleted branch — would be falsely rejected by the stated mechanism. The implemented checker instead queries `GET /repos/{owner}/{repo}/commits/{sha}` (200 = present; 404/422 = absent), which resolves any existing commit. If the owner prefers ls-remote literally, the fallback `git fetch origin <sha>` requires the server to allow fetch-by-SHA; the API route is the one that works everywhere GitHub hosts.
2. "In the report" is enforced as: full 40-hex form, in the `Claimed-SHAs:` field. Short SHAs do not satisfy EC-16 (collision + non-machine-checkable).

**Corrections.** None. Implementable as stated. Note for the record: the four cited SHAs are absent from every accessible location (verified in the D-cycle, worklog Task 33-d1d8: cat-file in all repos, fsck, text sweep, bundle sweep) — the loss claim stands, nothing was fabricated.

## EC-18 — Append-only evidence

**Failure pattern (verbatim).** Retroactive timestamps. The read-start marker was written with the write time.

**Rule (verbatim).** **EC-18 Append-only evidence.** Timestamps come from `date -u` at the moment of action, into a log that is never edited. Anything written later is labeled as reconstructed.

**Enforcement (verbatim).** The sequence checker fails on any log entry newer than its referenced action.

**Implementation mapping.** Enforcement point: `proposals/ci/evidence-sequence-check.yml` → `scripts/ci/evidence_sequence_check.py`. Log grammar: `## <ISO-8601 UTC> | <ENTRY-ID> | <verb> | <subject> [| RECONSTRUCTED]`. Checks implemented: timestamps parse as UTC; entries non-decreasing in time; ENTRY-IDs unique; with `--commit-time`, any entry whose claimed time drifts more than `--max-drift` (default 300 s) from the commit that carries it must be labeled `RECONSTRUCTED`.

**Corrections.** The stated check ("entry newer than its referenced action") needs a machine-readable notion of "referenced action". Implemented as: the entry's own timestamp IS the action time (written at action time by convention), so the checker enforces (a) monotonicity, (b) drift-between-claimed-and-commit-time with RECONSTRUCTED labeling. Backdated entries inside an append-only, forward-committed file are detectable exactly when the carrying commit is newer than the claimed time without a RECONSTRUCTED label. All-timestamps-same-host (`date -u` in one environment) is required to avoid cross-host clock skew; recorded as a condition of validity.

## EC-20 — Rulings are copied verbatim

**Failure pattern (verbatim).** Rulings implemented against their text. OD-07 bound only the coordinate hash. N8 defaulted to `per_atom`.

**Rule (verbatim).** **EC-20 Rulings are copied verbatim** into the work item, with acceptance tests named. A deviation needs a written waiver before coding starts.

**Enforcement (verbatim).** Each acceptance test must exist and pass. A test name that isn't in the diff fails.

**Implementation mapping.** Enforcement points: the work item carries the ruling text verbatim plus an `Acceptance-Tests:` field (test identifiers); CI job `acceptance-tests-in-diff` inside `verify-claimed-shas.yml` greps the PR diff for every named test identifier; a name absent from the diff fails. A deviation requires a waiver file under `docs/evidence/waivers/` referenced in the PR body (`Waiver:` field) BEFORE the first code commit (checked by commit order in the sequence checker).

**Corrections.** "A test name that isn't in the diff fails" requires test names to be machine-checkable identifiers (pytest node IDs or file paths). Renamed/refactored tests require a fresh work item or waiver; the linter is literal by design.

## EC-22 — Status vocabulary

**Failure pattern (verbatim).** "Pre-existing" failures claimed without a base comparison. Test claims without a CI run.

**Rule (verbatim).** **EC-22 Status vocabulary.** Only `RUN_PASS` with a run ID counts toward progress. Other states are `NOT_RUN`, `RUN_FAIL`, `PUSHED`, `MERGED`.

**Enforcement (verbatim).** Progress percentages are computed from CI run IDs, not stated by the coder.

**Implementation mapping.** Enforcement point: `proposals/ci/status-vocabulary-lint.yml` → `scripts/ci/status_vocabulary_lint.py`. Lint rules implemented: `RUN_PASS` must carry a run ID on the same line (`run <digits>` / `run_id=<digits>`); a percentage claim on a line without a run ID is rejected; the tokens "clean scan" and "pre-existing" without a run ID / base-SHA citation on the same line are rejected. Status tokens outside {NOT_RUN, RUN_FAIL, RUN_PASS, PUSHED, MERGED} are rejected.

**Corrections.** "Progress percentages are computed from CI run IDs" is an audit-side computation; the linter enforces the report-side half (no percentage without a run ID). Both halves together are implementable; the computation lives in the auditor's tooling, not in repo CI.

**Enforcement (verbatim).** Gitleaks runs on every branch in CI, including the one `main` currently lacks.

## EC-24 — Push log

**Failure pattern (verbatim).** A push by an unrecorded credential (`08a9403`).

**Rule (verbatim).** **EC-24 Push log.** Every push records the branch, SHA, time, and credential name in an append-only log.

**Enforcement (verbatim).** Only authorized credential names can push. A push outside the log fails the audit.

**Implementation mapping.** Enforcement point: `docs/evidence/push-log/PUSH_LOG.md` (append-only; started on this branch with RECONSTRUCTED backfill for all 2026-10-20 pushes, sourced from git commit metadata and the worklog, each labeled RECONSTRUCTED). The log's live entry for this branch's push is committed before the push and carries branch, SHA, time, credential NAME (`OWNER-PAT-1` — name only, never the value).

**Corrections (material — candidate ADVISORY clause).** GitHub does not record the credential identity on a push for a personal repository; there is no server-side enforcement point for "only authorized credential names can push" short of (a) an organization audit log, (b) one machine user / deploy key per credential so the committer identity carries the authorization, or (c) signed commits checked in CI. Until the owner selects one of those, the "log every push" clause is ENFORCED (the log is checkable post-hoc against `ls-remote` refs and git commit metadata), and the "only authorized names" clause is proposed for ADVISORY classification under the rule-authoring standard. This is the auditor's own discipline applied to the auditor's own rule.

## EC-25 — No deploy on push

**Failure pattern (verbatim).** The `main` deploy runs on every push, ungated.

**Rule (verbatim).** **EC-25 No deploy on push.** No workflow may deploy from a `push` or `workflow_run` trigger. Deploys are dispatch-only and gated.

**Enforcement (verbatim).** CI rejects any workflow file that has a deploy job on those triggers.

**Implementation mapping.** Enforcement point: `proposals/ci/no-deploy-on-push-lint.yml` → `scripts/ci/workflow_deploy_trigger_lint.py` (parses every `.github/workflows/*.yml`; deploy-detection regex over job IDs and job names: `\b(deploy|publish|rollback|release)\b`; forbidden triggers: `push`, `workflow_run`).
